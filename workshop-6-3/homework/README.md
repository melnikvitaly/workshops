# Workshop 6.3. Як працює FreeRTOS II: Черги (Queues) та Обмін даними між завданнями

## Task

  Реалізувати безпечну передачу даних від кількох датчиків до одного Consumer за допомогою xQueue

## Solution

Реалізовано на **ESP-IDF 6.0 для ESP32-C3** (PlatformIO, `framework = espidf`), C++,
класи — header-only, кожна задача в окремому файлі.

Два незалежні продюсери кладуть повідомлення в **одну** чергу, один consumer
їх звідти забирає і друкує в UART. Задачі не бачать одна одну: єдине, що вони
поділяють, — це `QueueHandle_t`.

```
BME280 (I2C)  ──► TemperatureTask ──┐
                                    ├──►  xQueue (8 × SensorMessage)  ──►  ConsumerTask ──► UART
LDR    (ADC1) ──► LightTask ────────┘
```

### Задачі

| Задача     | Файл                                                          | Пріоритет | Період                     | Що робить з чергою                     |
| ---------- | ------------------------------------------------------------- | --------- | -------------------------- | -------------------------------------- |
| `temp`     | [`TemperatureTask::run()`](src/tasks/TemperatureTask.hpp#L41) | 3         | 2000 мс, `xTaskDelayUntil` | `xQueueSend` з `SensorId::Temperature` |
| `light`    | [`LightTask::run()`](src/tasks/LightTask.hpp#L37)             | 3         | 500 мс, `xTaskDelayUntil`  | `xQueueSend` з `SensorId::Light`       |
| `consumer` | [`ConsumerTask::run()`](src/tasks/ConsumerTask.hpp#L33)       | 4         | блокується на черзі        | `xQueueReceive(..., portMAX_DELAY)`    |

Consumer має **вищий** пріоритет за обох продюсерів: він мусить забирати
повідомлення одразу, інакше сплеск від двох датчиків заповнить чергу і продюсери
почнуть впиратися в таймаут відправки.

### Повідомлення: tagged union

[`src/SensorMessage.hpp`](src/SensorMessage.hpp#L18):

```cpp
struct SensorMessage
{
    SensorId id;          // тег: каже, яке поле union дійсне
    uint32_t timestampMs; // nowMs() у момент вимірювання, не друку
    union
    {
        float   celsius; // дійсне лише якщо id == SensorId::Temperature
        uint8_t percent; // дійсне лише якщо id == SensorId::Light
    } value;
};
```

Чому це безпечно, а спільна глобальна змінна — ні:

- `xQueueSend` **копіює** структуру цілком, тому consumer працює зі своєю
  копією. Нічого не розділяється між задачами → не потрібен ані м'ютекс, ані
  `volatile`, ані критична секція.
- Планувальник може витіснити продюсера будь-де — але не *посеред* повідомлення:
  черга або прийняла його повністю, або не прийняла зовсім.
- `union` дає одну чергу на різнотипні дані замість двох черг. Ціна — дисципліна
  тега: [`ConsumerTask::print()`](src/tasks/ConsumerTask.hpp#L49) спочатку робить
  `switch (msg.id)` і лише потім читає відповідне поле. Читати «не те» поле —
  це undefined behaviour, і цей `switch` — єдине місце в програмі, де взагалі
  вирішується, яке поле дійсне.
- Додати третій датчик = одне значення в `enum` + одна гілка в `switch`.

### Черга переповнилась

Продюсери відправляють з обмеженим очікуванням
([`QUEUE_SEND_TIMEOUT_MS`](src/Config.hpp#L60), 10 мс), а не `portMAX_DELAY`:
якщо consumer з якоїсь причини завис, продюсер **втратить** зразок, залогує це
і збереже свій період. Це важливіше, ніж зберегти кожне значення: датчик, який
заблокувався назавжди на `xQueueSend`, — це мертвий датчик.

Consumer навпаки чекає `portMAX_DELAY` — задача заблокована, процесор між
повідомленнями не витрачається взагалі.

### Підключення

| Сигнал           | Пін       | Примітка                                     |
| ---------------- | --------- | -------------------------------------------- |
| BME280 SDA       | GPIO8     | + підтяжка 4.7 кОм до 3V3                    |
| BME280 SCL       | GPIO9     | + підтяжка 4.7 кОм до 3V3                    |
| BME280 VCC / GND | 3V3 / GND | адреса 0x76, SDO→GND (як у workshop 4-4/4-5) |
| LDR (дільник)    | GPIO0     | ADC1_CH0                                     |

**Важливо про GPIO8/GPIO9.** Це «канонічна» пара I2C на C3, але обидва піни —
strapping-піни, і на платах «C3 mini» вони зайняті:

- **GPIO8** керує вбудованим світлодіодом (адресний RGB на DevKitM-1, синій на
  SuperMini) — він блиматиме на кожній транзакції I2C. Вхід світлодіода
  високоомний, шину він не навантажує.
- **GPIO9** — це кнопка BOOT (підтягнута вгору, кнопка замикає на GND).
  Натискання BOOT під час роботи кладе SCL на землю і псує поточну транзакцію;
  [`BME280::readTemperature()`](src/hardware/BME280.hpp#L128) саме тому повертає
  `bool` і при помилці **нічого не кладе в чергу** замість того, щоб віддати
  сміття.
- Оскільки шина в спокої підтягнута вгору, режим завантаження це не ламає — але
  зовнішні підтяжки 4.7 кОм тут не рекомендація, а вимога: внутрішні ~45 кОм для
  цього замалі.

Перенести шину на тихішу пару (наприклад GPIO4/GPIO3, як у workshop 4-2) — це
два рядки в [`Config.hpp`](src/Config.hpp#L19).

### Калібрування LDR

[`LDR_RAW_MIN` / `LDR_RAW_MAX`](src/Config.hpp#L41) — це вручну виміряне вікно
дільника; відсоток рахується всередині нього
([`LDR::readPercent()`](src/hardware/LDR.hpp#L55)), а не від повного розмаху
0..4095, бо дільник із фоторезистором ніколи не проходить весь діапазон ADC.
Якщо покази ніколи не доходять ані до 0 %, ані до 100 % — треба перезаміряти ці
дві константи (залогувати сире значення в темряві та під ліхтариком).
Кожне читання — середнє з 16 вибірок: ADC на C3 шумить на десятки одиниць навіть
на ідеально стабільному вході.

### Збірка

```bash
pio run                      # збірка
pio run -t upload -t monitor # прошивка + UART 115200
```

Логи — штатний `ESP_LOGx` з окремим тегом на клас (`i2c`, `bme280`, `ldr`,
`temp`, `light`, `consumer`), тому рівень можна крутити і з `sdkconfig`, і в
рантаймі: `esp_log_level_set("ldr", ESP_LOG_WARN)`.
